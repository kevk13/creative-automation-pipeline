Implement Dropbox cloud storage support as the primary cloud adapter for the StorageAdapter pattern. The PDF’s Data Sources section names Azure, AWS, or Dropbox as the expected cloud storage backend. We previously scaffolded the StorageAdapter interface with LocalStorageAdapter implemented and S3/Azure/Dropbox as NotImplementedError stubs. This task implements the Dropbox adapter end-to-end and updates the run manifest, logging, and UI to reflect cloud storage usage.
Strategic context for code comments and README content:
Dropbox was chosen over S3 and Azure because the customer’s workflow is creative team-led. Creative and marketing teams at consumer goods companies consume assets in Dropbox-class shared storage, not in S3 consoles or Azure Blob containers. S3 and Azure remain scaffolded as single-class additions for engineering-side observability or hybrid dual-write architectures. The chosen adapter reflects user workflow, not just technical preference. Capture this rationale in inline code comments where the adapter is selected and in the README content prepared at the end of this task.
Implementation:
Install the official Dropbox SDK: npm install dropbox
Build out the DropboxStorageAdapter class that currently throws NotImplementedError. Implement against the existing StorageAdapter interface.
Required methods:
save(path, content, metadata?): Upload to Dropbox using filesUpload with mode overwrite. After upload, create a shared link via sharingCreateSharedLinkWithSettings. Return { url, bytes } where url is the shared link and bytes is content size.
load(path): Download from Dropbox using filesDownload. Return as Buffer.
exists(path): Use filesGetMetadata wrapped in try/catch. Return true if metadata returned, false on path/not_found error.
getUrl(path): Check for existing shared link first via sharingListSharedLinks. If none exists, create one via sharingCreateSharedLinkWithSettings. Return the public URL.
adapterName: Return string “dropbox”
Authentication:
Read access token from DROPBOX_ACCESS_TOKEN env var. If missing when the adapter is instantiated, throw a clear error message:
“Dropbox adapter requires DROPBOX_ACCESS_TOKEN environment variable. Generate a token at https://www.dropbox.com/developers/apps”
Create a .env.example file at the repo root with:
Storage adapter selection
STORAGE_ADAPTER=local
Set to “dropbox” and provide token to use Dropbox storage
STORAGE_ADAPTER=dropbox
DROPBOX_ACCESS_TOKEN=your_token_here
Path structure:
Maintain the same path structure as local: /outputs/{client}/{product}/{ratio}/{filename}. Dropbox stores this as a nested folder hierarchy. Client names with spaces should be slugified (lowercase, underscores) for path safety.
Retry behavior:
Apply the existing retry utility (built for Nano Banana) to Dropbox filesUpload and sharingCreateSharedLinkWithSettings calls. Same rules: 3 attempts max, exponential backoff with jitter (1s, 2s, 4s with plus or minus 20 percent jitter), retry on 429, 500, 502, 503, 504 and network errors, do not retry on 400, 401, 403.
Error handling:
Wrap all Dropbox API calls in try/catch. On failure: log structured error with operation, path, error type, error message. Do not crash the pipeline. Log the failure and continue processing remaining assets. If save fails after all retries, the run manifest marks that asset as uploadStatus failed with error details attached. Successful uploads get uploadStatus success and the shared URL.

Run manifest update:
The run manifest currently includes localPath and url per asset. Expand the per-asset record to:
{
“localPath”: “…”,

“adapter”: “dropbox”,
“uploadStatus”: “success”,
“uploadedAt”: “…”,
“bytes”: 245678
}
The adapter field makes the manifest self-describing across storage backends. When running with local storage, adapter is local and url is the local path.
